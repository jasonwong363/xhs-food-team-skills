# 自然表达与整组匹配

## 解决的失败

长篇产品介绍、报告式归因、机械同义改写，以及每条单看正确却接不到A的跟评。自然度不能由字数、表情数量或唯一句子数量证明。

## 执行顺序

1. 读取最新需求帖和总模板库，优先核对用户确认组合。区分平台原评论、用户确认执行稿和待确认生成稿；已入库不等于表达质量已获认可。
2. 写出该帖真正问的一个问题，选能直接回答的A句式。推荐帖报店并带必要理由；点单帖给点法；比较帖给区别。不为了贴题把标题重新说一遍。
3. 优先保留原句的口语节奏。评价仅供应具体事实，默认一处亮点；避免连续“我会提名／放入候选／推荐理由／比较适合这个口味”等分析措辞。不要靠换开头、堆感叹号和表情造差异。
4. 逐条选择B—E，记录它承接A的哪项内容。可以是尚未回答的具体询问、相关补充、简短反应；不要强制每组都填同样四种功能。同一组不能换几种说法重复问菜单，也不能A已报菜名、B又问吃什么、C再重复报菜。
5. 已确认完整组合只有在事实与主题都适配时优先保留。不适配则重选；不能为保留组合迁移未发生的到店、复购、朋友关系或地域身份。所有跟评是模板候选，不能宣称来自实际独立用户。
6. B—E继续逐字调库。问人均、辣度、位置可用原问句，不自动编答案。询问已由A回答的内容，或依赖未显示图片／前文的残句，换源。待确认来源标待审核，不升级为已验证。
7. 完成整批后连读开头、中间、结尾及全部特殊主题。标记连续相同开头、相同产品细节、重复整组，人工判断是否合理复用；不为了全量唯一造新场景。

## 归因与事实边界

“评价里有人三刷”不能变成“我三刷”；缺少本人回访事实时，不把A写成三刷者。可以给出候选推荐，但审计明确未提供回访经历，不当作已满足三刷证据。若唯一能成立的回答必须具备该经历而素材没有，标待核验。

整组被否定时保存整组原文和上下文，重选整组。用户未单独否定的“谢谢”“有菜单吗”等通用短句不应因此全库封禁；但不能把旧组仅调换顺序重新交付。原因诊断单独标为推断，不能冒充用户原因。

## 验证

检查品牌全称、非句首、无分店后缀、未编亲历、来源与替换、笔记字段保留。再做语义连读：直接回应、承接自然、无同组复述。结构检查通过不等于用户认可自然度；样稿与批稿一律待用户审核。仅重写规则或自评，不宣称通过盲测或质量提升验证。
