# 小红书评论模板调用与最小改写

## 任务

根据用户选定的评论模板库记录，输出 A 主评论和 B–E 跟评的原文或最小替换稿。A 与 B–E 是两种角色：A 独立成主评；B–E 是回复 A 的跟评，可以按用户规则从同类模板交叉调用。优先精确调取，用户明确要求替换时才改动。

用户授权用门店评价亮点写推荐理由时，A 可直接依据评价语料改写；B–E 继续调用评论模板。两种来源分别记录。

批量匹配或用户反馈“不自然、同质化、整批不行”时，先读取 [自然表达与整组匹配](references/natural-comment-matching.md)。先选语气和语境合适的原句／组合，再补必要事实；不能将评价亮点模式执行成整批产品介绍。

## 默认使用场景与交付层级

默认按用户已经真实到店处理，不因“像消费者”而拒绝。第一人称可以使用，但只能承载用户提供的实际菜品、感受和场景。调用前收集：身份、是否到店、实际吃到的菜、真实感受、同行/场景、可保留的强判断、不能写的内容。

- **参考草稿（默认）**：按模板提供表达方式，结合用户体验做最小替换，供用户修改；缺失事实保留为待核验项。
- **发布前稿**：用户要求定稿或发布前核验时，逐句检查体验、菜品、价格、地址和强判断，未确认的内容不进入成稿。
- 模板库只提供表达和结构。模板中的第一人称、复购、价格、口感或老板互动，不能因为出现在模板里就变成当前用户经历。

## 输入与前置检查

1. 读取本批评论模板库，并按 ID、原始文本、来源、审核状态、评论角色定位素材；不可只凭记忆或此前聊天片段代替当前库。
2. 若存在“用户确认模板组合”，优先读取并调用其中组合；未确认候选库只作补充，不覆盖用户确认组合。
3. 读取目标品牌/门店基准及本次明确的替换要求。评价亮点模式下，读取评价原文或可追溯的产品语料及评价ID／原始行号；A无需强行匹配现成评论模板。需要调库的角色没有库记录时，再请用户提供对应材料；已有资料不重复索取。
4. 输出前检查模板来源是否可访问、原文是否完整、是否为 A 或 B–E、审核状态是否可调用。缺项标注，不补造。

## 审核返工与否定记录

每轮筛选前读取品牌／项目反馈记录，交付前排查被否定原句及近似表达。用户反馈不行、要求剔除、重新匹配或只记录时，读取 [审核返工规则](references/review-rework.md)。区分“只记录”和“修改当前稿”，按批次、编号和旧原文定位；替换稿统一待审核。

## 改写规则

- **A 主评论（模板模式）**：优先按用户指定记录调用，并执行下方品牌表达规则。用户要求替换品牌、品类或产品时，做有依据的词项替换；保留原语气和强度，不新增无来源卖点。需要移动句首品牌或删除分店后缀时，记录改动。
- **B–E 跟评**：默认直接从可调用记录中调取原文，不润色、不重写、不擅自把原品牌、产品、地点改成目标品牌信息。只有用户明确指定替换且有事实依据时，才按同样的一对一方式替换。
- B–E 可跨来源选取时，内部保留每条来源ID，并注明“跨来源模板组合”；不得把它描述成原平台上真实存在的同一评论链。
- 不将跟评人为分为老客/新客，除非原话明确说明且用户要求此标签。
- 用户明确要求“微改写”时，可以在保留模板骨架的前提下替换品牌、品类、门店、菜品或产品描述；菜品替换必须来自目标品牌评价、菜单、用户确认资料或当前任务给出的模板组合。
- A 主评论尽量避免连续重复同一开头、同一强判断和同一产品细节；需要批量输出时，先从用户确认模板组合分散选取，再用目标品牌证据和当前用户体验做轻微替换。不要制造多个独立消费者身份。
- 模板与事实分开标记。涉及目标品牌的菜品、价格、地址、套餐、服务和体验承诺，必须能回到目标品牌资料、用户确认案例或本次明确指令；不能仅凭其他商家的模板原文当成目标品牌事实。

### 品牌表达与评价亮点推荐

- 评论中的品牌名默认不带分店后缀，如将“齐庆美蛙鱼头火锅（城北招商花园城店）”写成“齐庆美蛙鱼头火锅”。来源记录中的原店名保留，便于追溯；用户明确要回答地址／分店时按该次要求处理。
- A 的句首不出现品牌名，品牌放在句中或句尾。优先用自然的推荐表达，不把整批机械统一成“我推荐”。用户明确要求逐字引用时保留原文并说明与此规则的差异。
- **A 主评论（评价亮点模式）**：用户授权后，可用“推荐品牌＋具体理由”或“产品亮点＋推荐品牌”的结构。齐庆项目已于2026-09-28授权此模式，后续沿用，无需反复确认。默认只选一个与需求有关的具体亮点；需要比较两样或回答点单问题时才写两个。不强制补齐完整论证，不把“推荐理由、候选、评价里提到”等审计措辞拼进每条评论。确需引用他人评价才能成立的判断应保留归因，或改选无需该判断的模板，不能为口语化删掉必要归因。
- 示例：“我推荐齐庆美蛙鱼头，他们家的牛蛙超嫩。”这是用户认可的表达方式；品牌称呼沿用项目确认口径，具体口感与程度须由评价或用户体验支持，不要求每条照抄。
- 推荐理由可从门店评价中提炼，不必限制为原评论模板的一对一替词；标注为“评价亮点改写”，保留评价ID、原始行号和支持原话，不冒称逐字调库。分散使用有依据的亮点及句式，避免连续重复。
- 品牌同菜单且用户确认共用时，可复用菜品和口感语料；服务、位置、排队、价格、出品稳定性不能随之跨店套用。推荐意见不等于本人经历，不新增“我吃过”“三刷”等未提供事实，也不把单条好评写成每次保证。
- A 改完后检查与笔记及 B–E 的衔接。仅修改 A 时保留适配的跟评；失配项按审核返工规则处理，不静默改写整组。

## 输出

用户只要文案时，按以下格式交付，不附创意备选：

```text
A：{模板改写或按授权用评价亮点写成的推荐主评}
B回复A：{库内跟评原文}
C回复A：{库内跟评原文}
D回复A：{库内跟评原文}
E回复A：{库内跟评原文}
```

默认在文案后用一行简短来源记录标出模板ID或评价ID及可用状态；用户要求纯文案时可省去来源展示，但内部仍需保留映射。若原文不可直接用于目标品牌，说明具体缺少哪项体验或事实证据，输出参考草稿时保留待核验标记，不把模板经历改写成当前用户经历。

## 验收

- A、B–E角色正确，B–E确实回复A的结构只作为本次模板排版，不冒称真实原帖关系；
- 原文能按ID回溯，B–E默认逐字保留；
- 每处替换均能映射到用户明确要求或目标品牌证据；
- 批量生成时 A 不机械重复，菜品替换有目标品牌依据；
- 全量核对笔记→A→每条跟评：有直接回应、没有重复索要A已给出的信息、没有无来由的“+1”或替A承诺门店事实；不得按编号、取模、固定轮换池拼接B—E；
- 评论品牌无分店后缀，A不以品牌名开头；评价亮点模式下每条A均有具体推荐理由及评价来源；
- 不能直接使用的素材被标明原因，不混入可发布文案。
